# K053252 (CCU) registers, from MAME

```
python scripts/write_log.py xexex --regions k053252 --frames 600      # also orius, xexexa, xexexj
python scripts/write_log.py xexex --regions k053252,... --frames 2400 --summary --from 600
```

MAME 0.289, `mame.exe` from `C:/Emulation/Emulators/MAME`. Register = (address - `0d0000`) / 2,
low byte (`umask16(0x00ff)`, `xexex.cpp:583`).

## Writes

The same eleven bytes in all four sets, written twice: frame 0 (line 48, PC `001366`-`0013b6`) and
frame 515 (lines 42-43, PC `00179a`-`00184e`). After that only register `0e` is written, once a
frame at line 258 (PC `00531a`), the INT1 acknowledge.

| reg | value | MAME meaning (`k053252.cpp` header, `write()`) |
|---|---|---|
| 00-01 | `01 ff` | HC = `0x1ff` + 1 = 512 |
| 02-03 | `00 21` | HFP = 33 |
| 04-05 | `00 37` | HBP = 55 |
| 06 | `01` | INT1EN |
| 07 | not written | INT2EN |
| 08 | not written; MAME resets it to `01` (`device_reset`) | VC high |
| 09 | `20` | VC = `0x120` + 1 = 289 (with reg 08 = `01`) |
| 0a | `0c` | VFP = 12 |
| 0b | `0e` | VBP = `0x0e` + 1 = 15 |
| 0c | `54` | VSW = 5 + 1 = 6, HSW = 4 + 1 = 5 |
| 0d | not written | INT-TIME |
| 0e | per frame | INT1ACK |

The game writes the table `01 ff 00 21 00 37 01 20 0c 0e 54` to registers 0-6 and 9-c, skipping 7
and 8. Read against the GX layout, its `01` lands in INT1EN and VC's high byte is never written;
MAME's `device_reset` presets reg 08 to 1 for this (comment at `k053252.cpp`, `device_reset`). If
the chip's reset value of reg 08 is not 1, VC would be `0x020` + 1 = 33: unverified, no PCB.

## Derived totals (MAME's formulas, `res_change()`)

| | total | visible | front porch | sync | back porch |
|---|---|---|---|---|---|
| horizontal, pixels | 512 | 512 - 33 - 55 - 8*5 = 384 | 33 | 8 * HSW = 40 | 55 |
| vertical, lines | 289 | 289 - 12 - 15 - 6 = 256 | 12 | 6 | 15 |

At 8 MHz (`32 MHz / 4`, `xexex.cpp:726`): HSync 8e6 / 512 = 15.625 kHz, VSync 15625 / 289 =
54.0657 Hz.

MAME's `res_change()` runs on these writes and reconfigures the screen to the same geometry: the
screen stayed 384x256 at 54.065744 Hz for all 600 frames (`# screen` lines in `writes.log`).

## Comparison

| source | H total | V total | visible | HSync | VSync |
|---|---|---|---|---|---|
| K053252 registers | 512 | 289 | 384 x 256 | 15.625 kHz | 54.0657 Hz |
| driver `set_raw(8 MHz, 512, 40, 424, 289, 0, 256)` | 512 | 289 | 384 x 256 | 15.625 kHz | 54.0657 Hz |
| PCB note (`xexex.cpp:74-75`) | | | | 15.367 kHz | 54.0657 Hz |

The registers agree with the driver's `set_raw` on every total. The PCB note's VSync agrees with
both; its HSync does not (15.367 kHz x 289 lines would give 53.17 Hz; 15.367 kHz at 54.0657 Hz is
284.2 lines). Take 512 x 289 at 8 MHz.

Not derivable from MAME: where sync sits relative to the visible window. MAME places visible at
pixels 40-423 by `set_offsets(40, 0)` and `set_raw`'s `hbend = 40`, not from HFP/HBP/HSW (its TODO:
"understand how to interpret the back / front porch values").
